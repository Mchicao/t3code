# Remote SWARMS Control Boundary

> For maintainers. This is a fork-specific decision record; implementation is pending.

**Status:** Accepted for fork implementation.

## Decision

The first remote-agent feature is one SWARMS workflow executed on PC B and controlled from PC A through the existing authenticated T3 Connect environment connection.

T3 is the control plane. It authenticates the caller, selects an environment-local project, starts and tracks the run process, exposes a bounded run snapshot, and requests cancellation. SWARMS is the execution plane. It owns workflow validation, task scheduling, provider routes, ACP/CLI transports, concurrency limits, worker state, artifacts, and reports.

The feature does not create one T3 thread per SWARMS task. It does not use a terminal RPC as an execution API, copy provider credentials through T3, or modify the T3 Connect tunnel protocol.

## Ownership

| Concern                                                         | Owner                                      |
| --------------------------------------------------------------- | ------------------------------------------ |
| Relay access, bearer/DPoP authentication, and RPC authorization | T3                                         |
| Environment and project selection                               | T3                                         |
| Workflow plan validation and task DAG                           | SWARMS                                     |
| Provider credentials and provider-specific transports           | SWARMS on PC B                             |
| Global/provider concurrency and retries                         | SWARMS                                     |
| Durable task snapshots, events, artifacts, and report           | SWARMS state contract                      |
| Run process lifecycle and cancellation request                  | T3, using its process supervision boundary |
| Public run snapshot exposed to PC A                             | T3 projection of SWARMS state              |

## Lifecycle

1. PC A resolves PC B through the existing `RelayConnectionTarget` and `EnvironmentSupervisor`.
2. The client sends a typed remote-SWARM start command with an environment-local `projectId` and an opaque, bounded SWARMS plan JSON document.
3. T3 validates authorization and project ownership, creates a server-owned plan file, and starts the configured SWARMS executable with fixed arguments. The client never supplies an executable, arbitrary working directory, provider credential, or raw process arguments.
4. SWARMS runs from the server-configured SWARMS root and receives the selected project workspace through `--workspace-root`. The run id is generated by T3 and validated with SWARMS-safe path rules.
5. T3 returns acceptance with the run id. Later reads derive the current snapshot from `workflow.json`, `tasks/*.json`, and `report.json` or `report-rs.json`; T3 does not rewrite SWARMS state.
6. A cancel command is idempotent and requests termination of the owned run process. The public state becomes cancelled only after termination is observed. If the process tree cannot be confirmed stopped, T3 reports that failure instead of claiming cancellation.

## v1 Boundary

The typed control surface has three operations:

- `start`: submit one plan for one existing project and return a generated run id;
- `get`: return a bounded run and task snapshot for one run id;
- `cancel`: request and observe run termination.

The initial surface is API-first. A visual dashboard, per-task T3 threads, live steering, automatic WSL discovery, cross-project dispatch, merge coordination, and automatic resume after a T3 server restart are outside v1.

The runner command and SWARMS root are server configuration, not client input. A native Windows or native WSL deployment is supported when the configured T3 server process can execute the SWARMS command. Automatic Windows-to-WSL path translation is not part of v1.

## Security Invariants

- Remote writes require the existing `orchestration:operate` scope; reads require `orchestration:read`.
- The client selects a project id, never an arbitrary filesystem path. T3 resolves the project root on PC B.
- The plan is written to a server-owned file and is never placed in a command-line argument.
- T3 never forwards provider tokens, local environment files, or raw worker logs to PC A as part of the v1 snapshot.
- The public snapshot contains bounded lifecycle, task, and report metadata without prompts or secrets.
- Unknown, malformed, or partially written SWARMS state is an explicit unavailable/error result, never inferred success.

## Rationale

SWARMS already provides the requested mass-launch behavior, ACP/CLI execution, provider caps, durable state, and reports. T3 already provides the authenticated cross-machine connection, environment-scoped RPC, and authorization model. Keeping those responsibilities separate avoids duplicating a scheduler in T3 and avoids coupling T3 contracts to SWARMS provider implementations.

The alternative of creating one T3 thread per worker would make T3 the scheduler, multiply orchestration state, and lose SWARMS' existing concurrency and run-report semantics. It remains a possible future adapter, not the first implementation.
